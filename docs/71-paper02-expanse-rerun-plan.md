every simulation that paper 02 reports under Hendrickson's published

instead, only the `--params` value changes; the budget is unaffected.

## 3. Code changes before any submission

All are Phase 0 items of `docs/70`, restricted to what paper 02
needs. Each is committed before submission, because simrun runs the
committed tree only.

1. **Published parameters.** Add `published_resp_param()` and
   `published_baseline_param()` built from `data/extracted_rp.rda`
   and `data/extracted_bp.rda`; rename the current pair to
   `simcore2026_*()` and correct the comment that calls them
   Hendrickson's defaults.
2. **One switch.** `simulation-core.R` reads the set from an
   environment variable or a `--params published|simcore2026|fixture`
   argument parsed once, replacing the seven hard-coded calls (lines
   436, 1061, 1328, 1415, 1508, 1614 and 1695) and the direct calls in
   `32-run-g9-gap-fill.R` (line 166), `36-run-referee-variants.R`

   `meta.rds` records the set name and the parameter values.
3. **G10 in the same job.** Add `'E7null_cr2'` to the default
   `g_specs` of `simulate_cell_combined()`, so jobs 27, 21 and blocks
   A to C fit G9 and G10 to the same trials. This retires the G10
   backfill (`41-run-g10-backfill.R`) and its pairing guard.

   `analysis/data/carryover-sensitivity/published/<family>/`, leaving
   the sim-core outputs in place for the provenance record and any

## 4. Expanse readiness (no project job has run there yet)

Infrastructure was verified piece by piece on 2026-10-26 (vignette,
`~/dotfiles/share/simrun/vignette.md`, 'Using simrun on Expanse'),
and `simrun-server-slurm` already passes `--nodes=1`,
`--constraint=lustre`, `--cpus-per-task` and the `sds154` account,
and the job wrapper exports `SIM_CORES`. No project job has run end
to end: no `analysis/remote_runs/*-expanse` directory exists.

1. **Session login.** `ssh expanse true` by hand, to answer the TOTP
   prompt; the multiplexed connection lasts four hours, so long
   monitoring sessions need a fresh login.
2. **Remaining balance.** `expanse-client user -r expanse` on the
   login node. The trial allocation is 1000 core-hours, a hard cap,
   through about 2027-04-20 (six months from 2026-10-20).
3. **Image.** No current local image exists (the only one is
   `ghcr.io/rgt47/pmsimstats-ng:b9c4bbd`). Run `make docker-build`
   (default `PLATFORM = linux/amd64`, which Expanse needs) at the
   submission commit; simrun checks the hash label against
   `Dockerfile` plus `renv.lock` before shipping. The image is about
   5.5 GB, so the first `--ship` takes a while.
4. **Memory charging (to verify).** On Expanse's `shared` partition a
   job is believed to be charged by whichever is larger, its cores or
   its memory as a share of a node (about 2 GB per core). Requesting
   24 GB for 8 cores, as on zeus, would then be charged as 12 cores.
   Confirm in the Expanse user guide and size `--mem` from the
   measured peak (step S2) rather than from the zeus settings.

## 5. Budget

**Assumptions (not yet measured).**

- Expanse per core runs at about half of julia's speed (verified
  with the base-R benchmark, 2026-10-26). Zeus's per-core speed
  relative to julia has not been measured; the estimates below take
  zeus as equal to julia, so Expanse costs **twice** the zeus
  core-hours. Mercury is taken as half of zeus (config note).
- Fitting G10 inside each combined job adds about **20 percent** to
  that job (one more AIC grid and refit per replicate). Not measured.
- The noisier published parameters do not materially change fit time
  or convergence. Plausible, not checked.

Block A is split by sub-block from the job 31 and 33 times (`A1-dropout` at
about 24 zeus core-hours per 12,000 cell-replicates, `A2-size` at about 16),
which keeps every job under eight hours. The trimmed run plus
calibration is about **540 core-hours**, a little over half the
allocation, leaving about 450 for failures, one rerun of the largest
job and paper 10. The 2x factor is the largest uncertainty; step S2
measures it and step S3 is a hard go/no-go gate on the result.

**The zeus alternative.** The same work took about 45 hours of
wall-clock time on zeus, run serially, at no allocation cost. Expanse
buys concurrency: every job can run at once, so the whole set takes
roughly one working day of wall-clock time instead of two to three
days, and zeus stays free for paper 01's driver 19 and the Phase 3
papers. That trade is sound only if those zeus jobs are actually
queued; otherwise zeus alone is the cheaper choice. A split
(the large blocks on Expanse, the rest on zeus) is allowed, subject
to the pairing rule in Section 6.

## 6. Pairing and platform rule

Results are not draw-for-draw identical across platforms (different
CPUs and BLAS kernels, even with the same image).

- Within a job, every specification is fitted to the same trials, so
  within-job paired comparisons (G9 against G10, the ladder rungs on
  job 27) are safe on any host.
- **Job 27 and the E0 isolation (job 42) must run on the same
  host**: `39-check-e0-isolation.R` reproduces E0 and G1 of job 27 on
  a subset, and the ladder reads both.
- **Blocks A and B** are assembled into one summary by
  `33-assemble-gap-fill.R`; run them on one host and one commit so the
  table has a single provenance.
- The referee-variant blocks have their own seeds per cell and are
  unpaired by design; they may run anywhere.
- All production jobs run at one commit and one image hash. Any
  commit after the first production submission that touches
  `simulation-core.R` invalidates the jobs already submitted.

## 7. Execution steps

### S0. Prerequisites (local, no allocation)

1. Code changes of Section 3, committed; the moment check passes;
   tinytest passes.
2. Local smoke for each driver under `--params published` at two or
   three replicates (`01-run-factorial.R --smoke`, the `--dev` modes
   where they exist), so failures surface before Expanse is charged.
3. `make docker-build`; confirm the image's architecture is amd64 and
   its `zzcollab.dockerfile.hash` label matches the commit.
4. Section 4 checks: login, balance, `SIMRUN_ROOT` on Lustre project
   storage.

### S1. Smoke job on Expanse (about 1 core-hour)

```
simrun --host expanse submit --ship --cores 4 --mem 8 \
  --time 00:30:00 --label p02-smoke -- \
  Rscript analysis/scripts/carryover-sensitivity/01-run-factorial.R \
  --smoke --params published
```

Pass criteria: the `.sif` builds; the job reaches `running` and
`done` with exit 0; `simrun --host expanse fetch` lands
`analysis/remote_runs/job-N-<sha>-expanse/` with `provenance.yml`
recording host, partition and image digest.

### S2. Calibration job (about 12 core-hours)

Rerun stored job 35 (referee block A: 0.71 hours on 8 zeus cores)
under the **sim-core** set, same command and seed, at 16 cores:

```
simrun --host expanse submit --cores 16 --mem 32 --time 02:00:00 \
  --label p02-calib-refA -- \
  Rscript analysis/scripts/carryover-sensitivity/36-run-referee-variants.R \
  --block A --cores 16 --params simcore2026 \
  --out-dir analysis/data/carryover-sensitivity/expanse-calib/block-A
```

It measures three things:

1. **Speed ratio** $r$ = Expanse core-hours / 5.7 zeus core-hours.
2. **Peak memory per worker** (`sacct -j <id> --format=MaxRSS,ReqMem`
   on the login node), which sets `--mem` for production.
3. **Cross-platform reproducibility**: whether the per-replicate
   estimates equal job 35's. If they agree to numerical tolerance, the
   pairing rule of Section 6 can be relaxed; if not, it stands.

### S3. Go/no-go gate

Projected cost = $r \times 264$ zeus core-hours, with the 1.2 G10
allowance replaced by the measured overhead. Proceed on Expanse if the projection plus 25 percent reserve
fits the remaining balance. Otherwise move job 27 plus the E0 isolation
(one pair, about 65 zeus core-hours) and the factorial to zeus, keep
blocks A and B and the referee blocks on Expanse, and recompute.

`--mem` from S2, `--time` at 1.5 times the projected wall-clock time
so a hung job (compare zeus job 52) cannot drain the allocation.
Projected wall-clock times assume $r = 2$.

## 9. Risks

- **Budget.** The 2x factor and the 20 percent G10 overhead are
  assumptions; S2 and S3 exist to bound them before most of the
  allocation is spent.
- **Hung jobs.** Zeus job 52 ran 118 hours on a block that took 13.5
  hours elsewhere. The cause is unknown; `--time` limits cap the loss
  on Expanse, but a repeat would cost a resubmission.
- **Login window.** TOTP every four hours makes unattended monitoring
  impossible; fetches wait for the next login.
- **Queue waits.** The `shared` partition is shared with other users;
  sixteen-core jobs normally start quickly, but this is not
  guaranteed.
- **Scope creep.** The companion prognostic paper (jobs 28 and 30,
  about 69 zeus core-hours) carries the same parameter defect and
  would roughly exhaust the remaining reserve; plan it separately.
